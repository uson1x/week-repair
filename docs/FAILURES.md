# Execution findings

These findings come from execution during development on 2026-10-11. Controlled tests and live provider failures are labeled separately.

## 1. The Reviewer rejected a correct clarification

**Evidence type: actual cross-agent failure in a live Codex run.** In the [original impossible-week run](../examples/impossible-required/result.json), two required 30-minute runs had to fit into the only remaining day, which allowed 30 minutes and one session. The Planner correctly asked which constraint could change. All deterministic checks passed.

The Reviewer recognized that the question was necessary and specific, but rejected it because a schedule could not yet be approved. This repeated across all three attempts. The workflow exhausted its two repair rounds and returned `blocked` after 70,682 ms. The [original trace](../examples/impossible-required/trace.json) preserves each rejection.

The Reviewer contract had conflated two meanings of approval: accepting a useful response and approving an executable schedule. The fix made the distinction explicit. The Reviewer may accept a necessary clarification; the workflow still returns `needs_clarification`, and only a valid `ready` proposal can become an approved schedule. The report labels this case “Reviewer accepted the question.”

The [fixed live run](../examples/impossible-required-fixed/result.json) returned `needs_clarification` on its first attempt in 22,352 ms, with no deterministic violations. The Reviewer accepted the specific question without pretending a schedule was ready. Compare the [before report](../examples/impossible-required/report.html) and [after report](../examples/impossible-required-fixed/report.html).

This was a state-interpretation error between agents. It did not require weakening the scheduling rules or increasing the retry limit.

## 2. An array passed an enum check

**Evidence type: controlled malformed-output regression.** This was a real validator defect found with an injected value, not an error spontaneously generated by a live model.

The test `enum values must be strings; arrays cannot impersonate valid actions or statuses` supplied an action such as `['move']`. The validator checked membership after calling `String(value.action)`. A single-element array becomes the string `move`, so it passed that check. The first run returned a completed-session preservation error but missed the expected `action must be` error: 13 tests passed and one failed.

The fix replaced string coercion with direct comparisons for every enum member, including proposal status and action. The focused rerun passed all 14 tests:

```sh
node --import tsx --test tests/validate.test.ts
```

See [the regression test](../tests/validate.test.ts) and [the validation boundary](../src/validate.ts). A structured-output schema is useful, but the application must still reject invalid runtime types.

## 3. The first Claude CLI run could not authenticate

**Evidence type: live provider execution failure.** The first Claude CLI attempt stopped at the Planner stage with `Claude exited with 1`; its diagnostic output reported `Not logged in`. No plan was approved and no Reviewer call completed in that run. This was a local authentication problem, not a scheduling or model-reasoning failure.

The blocked result was captured at `2026-10-11T20:33:59.205Z`. The final implementation uses the available Codex CLI login. The unused Claude adapter was removed.

## 4. The final provider completed live repairs

**Evidence type: actual Codex CLI execution with synthetic input.** The saved [result](../examples/disrupted-week/result.json), [stage trace](../examples/disrupted-week/trace.json), and [HTML report](../examples/disrupted-week/report.html) record a run started at `2026-10-11T20:37:06.848Z`, using `live:codex-cli:gpt-6.1-sol`.

The Planner took 14,385 ms, deterministic validation took 8 ms, and the independent Reviewer took 9,083 ms. Total elapsed time was 23,480 ms. The first proposal passed validation and review; no repair retry was needed. It moved the missed hard run to Thursday and dropped an optional recovery session to meet the weekly limit. Completed work and all required sessions were preserved.

This run proves that both live model stages executed for this scenario. It does not measure production reliability or prove that a live retry will converge. Controlled workflow tests cover retry and blocked paths.

The [equipment-restriction scenario](../examples/equipment-restriction/result.json) also completed live with an approved result in 21,232 ms. It dropped only the optional session requiring unavailable gym equipment and preserved completed work and required runs.
